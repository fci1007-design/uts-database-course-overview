## 先知道：這門課到底在學什麼？

這門課在教你：**怎麼把資料有條理地存起來、把需要的資訊找出來，以及避免資料互相矛盾。**

例如，一家相機店有商品、製造商、相機、鏡頭與相容性資料。店員可能想知道「某廠商有哪些商品」「哪些鏡頭能搭配某台相機」「各廠商有多少種商品」。這些問題背後，都需要先把資料整理好，再用查詢取得答案。

整門課的主線如下：

| 單元／週次 | 在教什麼 | 讀完至少要能回答 |
|---|---|---|
| 單元一，第 1–2 週 | 認識資料庫，用 SQL 查資料 | 我要的資訊在哪裡？要怎麼找？ |
| 單元二，第 3 週 | 畫 ERD、設計並建立資料表 | 資料應該分成哪些表？彼此怎麼連？ |
| 單元三，第 4–5 週 | 完整性、交易、權限與正規化 | 怎麼防止資料錯亂、重複與不一致？ |
| 單元四，第 6 週 | 網球與公車的完整案例 | 怎麼把前面學的用在一個完整情境？ |

你可以先把學習目標放在「能解釋資料的關係、看懂重要查詢、判斷結果是否合理」。完成本課作業仍需要實際執行 SQL，但不用等到熟記語法，才能開始理解這門課。

## 單元一：資料已經在裡面，我要怎麼找到答案？

### 1.1–1.5：先認識資料庫和 SQL

這部分從「為什麼要用資料庫」開始。試算表適合許多個人整理與分析工作；當多種資料互相關聯、多人要共同使用，而且需要一致的規則時，資料庫能提供集中管理與檢查機制。

最重要的觀念是：**資料先分門別類保存，需要時再連起來使用。** 例如，製造商名稱放在製造商表，商品表記錄它屬於哪個製造商，便不必在每筆商品重寫一整份廠商資料。

這幾節也讓你看懂教師的腳本：有些指令負責建表，有些放入範例資料，有些才是在查答案。不需要一開始就讀懂整份程式。

> **商業例子｜連鎖商店共用商品資料**
>
> 門市與倉庫都要知道商品的售價與供應商。若各自保存不同版本，可能出現報價不一致。把商品資料集中管理，雙方就能依同一個商品編號讀取資料。


### 1.6–1.6.7：從一張表找資料

這部分教你挑欄位、設條件、排序、計算與統計。

| 課程內容 | 實際在解決什麼問題 |
|---|---|
| 選取欄位、比較條件、排序 | 只看需要的資訊，例如找出一萬元以上商品，按價格排列。 |
| 計算欄位 | 查詢時算出新資訊，例如折扣價；不一定要修改原始售價。 |
| 聚合函數：`COUNT`、`SUM`、`AVG`、`MAX`、`MIN` | 算筆數、總和、平均、最大與最小值。 |
| 篩選：`AND`、`OR`、`IN`、`LIKE` | 組合條件，或找符合某種文字樣式的資料。 |
| 去除重複：`DISTINCT` | 讓查詢結果只列出不同的值；不會刪掉原始紀錄。 |

第一個值得看懂的 SQL：

```sql
SELECT product_name, price
FROM product
WHERE price >= 10000
ORDER BY price DESC;
```

整句意思是：「從商品表，找出價格至少一萬元的商品，顯示名稱和價格，從貴到便宜排列。」掌握 **`SELECT` 看什麼、`FROM` 去哪找、`WHERE` 挑哪些、`ORDER BY` 怎麼排**，就能開始閱讀很多基本查詢。`SELECT *` 的星號則表示所有欄位。

> 本文 SQL 使用虛構的商品與製造商表作概念示意，不是教師資料庫中的既有表，也不是可直接交作業的答案。

> **商業例子｜找出適合促銷的高價商品**
>
> 假設 A 相機售價 24,000 元、B 鏡頭 6,000 元、C 鏡頭 12,000 元。主管要看「至少一萬元的商品」，並從貴到便宜排列，結果就是 A 相機、C 鏡頭。這正是上面 SELECT 的用途。


### 1.7–1.7.4：答案需要多張表，或需要先算再查

**連接 JOIN：把相關資料對起來。**

假設商品表只記製造商編號，製造商表才有名稱。想一起看到商品名稱與廠商名稱，就需要連接：

```sql
SELECT p.product_name, m.manufacturer_name
FROM product AS p
JOIN manufacturer AS m
  ON p.manufacturer_id = m.manufacturer_id;
```

你要理解的是「用相同的製造商編號找到對應資料」。`p`、`m` 只是兩張表的簡稱。

本課特別會用到 `NATURAL JOIN` 和交叉乘積表示法。自然連接會用兩表所有同名欄位配對；交叉乘積則先考慮所有組合，再用條件留下正確配對。**連接條件不完整，即使指令能跑，答案也可能錯。** [PostgreSQL 官方說明](https://www.postgresql.org/docs/current/queries-table-expressions.html)

其餘幾節各有一個核心用途：

| 章節／觀念 | 你需要掌握的大意 |
|---|---|
| 1.7.1 `GROUP BY` 與 `HAVING` | 把紀錄分組後做統計，例如每個廠商有幾種商品。`WHERE` 先篩選個別紀錄，`HAVING` 再篩選統計後的群組。 |
| 1.7.2 子查詢 Subquery | 一個查詢裡面放另一個查詢，例如先找出最高價格，再找哪些商品符合。 |
| 1.7.3 視圖 View | 把常用查詢取個名字，之後方便使用；一般視圖保存的是查詢定義。 |
| 1.7.4 自我參照與自連接 | 同類資料也可能彼此有關，例如員工的主管也是員工；查詢時可以讓同一張表分別扮演員工與主管。 |

另一個值得認得的 SQL：

```sql
SELECT manufacturer_id, COUNT(*) AS product_count
FROM product
GROUP BY manufacturer_id
HAVING COUNT(*) >= 2;
```

意思是：「按製造商分組計算商品數，只顯示至少有兩筆商品的製造商。」這就是從「看一筆資料」進到「看一群資料」。

> **商業例子｜列出廠商名稱與商品數**
>
> 商品表記錄製造商編號，製造商表記錄廠商名稱。店長要看「哪個廠商供應哪些商品」，就需要 JOIN；若改問「每家廠商供應幾種商品」，就需要分組統計。


**這個單元學到的能力：把日常問題轉成『資料來源、條件、關聯與統計方式』。**

## 單元二：資料庫應該怎麼設計？

單元一多半使用現成資料庫；這一單元開始思考，資料表最初應該怎麼安排。

### 2.1–2.4：畫出資料與關係

ERD（Entity Relationship Diagram，實體關係圖）就是資料庫的設計圖。它交代有哪些事物、要記錄哪些屬性，以及事物之間怎麼關聯。2.4 是 ERD 建立的拓展案例。

例如：

- **實體 Entity**：要記錄的事物，例如學生、課程、商品。
- **屬性 Attribute**：事物的特徵，例如學號、姓名、售價。
- **關係 Relationship**：事物之間的連結，例如學生選修課程。

兩個重要的識別工具：**主鍵 Primary key** 用來唯一辨識一筆紀錄，例如學號；**外鍵 Foreign key** 用來指向另一張表的紀錄，例如商品所屬的製造商編號。姓名可能重複，因此通常不適合直接拿來識別學生。

關係也有不同形式：

| 關係 | 例子與意義 |
|---|---|
| 一對一 | 假設校規規定一名學生最多對應一份在校住宿檔案，反過來亦然。 |
| 一對多 | 在「每件商品只有一個製造商」的假設下，一個製造商可以有多件商品。 |
| 多對多 | 一個學生可以修多門課，一門課也可以有多個學生。 |

多對多通常增加一張**關聯表**處理，例如「選課表」記錄學生編號與課程編號，也能放成績。它把多對多拆成兩個一對多。若要管理重修或不同學期，還需要把學期等條件納入設計。

看到 ERD 上的「零、一、多」，要想到：這個關係可不可以沒有？最多可以有幾個？**這些是情境規則，必須先理解需求才能決定。**

> **商業例子｜訂單為什麼需要訂單明細**
>
> 一張訂單可以買多項商品，同一項商品也可以出現在不同訂單。可增加「訂單明細」，記錄訂單編號、商品編號與數量，連接訂單和商品；不必把所有商品名稱塞進訂單的一個欄位。


### 2.5–2.10：把設計變成真的資料表

這部分介紹建立資料庫、建立資料表與關聯表，以及新增、修改、刪除資料。你先認得每種指令的工作即可：

| 指令 | 用途 |
|---|---|
| `CREATE DATABASE`／`CREATE TABLE` | 建立資料庫／資料表，定義欄位與規則。 |
| `INSERT` | 放入新的紀錄。 |
| `UPDATE` | 修改既有紀錄。 |
| `DELETE` | 刪除紀錄。 |
| `DROP TABLE` | 移除整張資料表及其資料。 |

設計欄位時也要選**資料型別**：數量可能用整數，名稱用文字，生日用日期。型別取決於資料意義；電話雖然長得像數字，通常當文字處理，才能保留開頭的 0 等內容。

這裡要分清楚：`SELECT` 查資料，`INSERT`／`UPDATE`／`DELETE` 改資料。尤其 `UPDATE`、`DELETE` 的條件會決定影響範圍，沒有 `WHERE` 可能改動或刪除整張表的所有紀錄。

> **商業例子｜商店維護商品目錄**
>
> 上架新商品用 INSERT；調整售價用 UPDATE；刪掉誤建的測試商品用 DELETE。已出現在正式訂單的商品，停售時通常保留紀錄並變更狀態，讓歷史訂單仍有資料可查。


**這個單元學到的能力：把一段需求，轉成有明確身分、欄位與關係的資料表。**

## 單元三：怎麼讓資料保持可信？

這一單元關心的是：「資料即使存進去了，會不會其實不合理？」例如同一學號出現兩個人、商品指向不存在的製造商，或商品價格變成負數。

### 3.1–3.2.4：完整性與約束

**資料完整性 Integrity** 是維持資料正確、一致並符合規則。**約束 Constraint** 則是交給資料庫自動檢查的規則。

| 完整性 | 要避免的問題 | 常見方法 |
|---|---|---|
| 實體完整性 | 不知道這是哪一筆，或識別編號重複。 | 主鍵不能重複，也不能是 `NULL`。 |
| 參照完整性 | 指向另一張表中不存在的紀錄。 | 用外鍵檢查關聯。 |
| 域完整性 | 欄位內容不符合允許的範圍或形式。 | 資料型別、`NOT NULL`、`CHECK` 等。 |

例如 `CHECK (price >= 0)` 要求價格不能是負數；若價格也必須填寫，還要有 `NOT NULL`。`NULL` 表示缺少或未知的值，不能直接當成 0。 [PostgreSQL 約束說明](https://www.postgresql.org/docs/current/ddl-constraints.html)

刪除有關聯的資料時，也要決定規則：例如廠商還有商品時禁止刪除，或在合適情況下一併刪除相關紀錄。重點是知道後果，並讓設計符合需求。

> **商業例子｜擋下不合理的訂單**
>
> 商店不希望訂單編號重複，也不接受明細指向不存在的商品，或購買數量是負數。主鍵、外鍵與欄位檢查各自處理不同問題，讓這些規則不只靠店員記得。


### 3.3：交易 Transaction

交易是把一組操作當成一個整體。例如轉帳包含「甲扣款、乙入款」，不能只完成其中一半。`COMMIT` 確認這組變更，`ROLLBACK` 則取消尚未提交的變更。

教材的 **ACID** 是四項特性：原子性（整組成功或失敗）、一致性（維持定義的規則）、隔離性（控制同時操作的相互影響）、持久性（提交後的保存保證）。交易能協助維持一致，業務規則仍須正確設計。 [PostgreSQL 交易入門](https://www.postgresql.org/docs/current/tutorial-transactions.html)

這節也會談日誌與死結。先知道日誌協助記錄變更與復原；例如兩筆訂單各自鎖住一項商品的庫存，又等待對方鎖住的另一項商品，就可能形成死結；資料庫通常需要中止其中一筆交易，才能繼續處理。

> **商業例子｜接單與扣庫存一起完成**
>
> 一筆訂單買兩個鏡頭，系統要新增訂單並扣減庫存。若新增訂單失敗，已扣的庫存也應撤回，避免有扣貨卻沒有訂單。交易把這組操作一起處理；庫存是否足夠仍需另外檢查。


### 3.4：SQL 授權

這部分決定**誰可以對哪些資料做什麼事**。例如報表人員能查詢，但不一定能刪除資料；`GRANT` 授予權限，`REVOKE` 撤回權限。

要分清楚：權限處理「可不可以操作」，完整性處理「這樣的資料合不合理」。

> **商業例子｜門市與主管有不同權限**
>
> 門市人員可以查庫存與新增訂單；主管可以調整售價；只看報表的同仁不需要刪除訂單的權限。先決定各角色能做什麼，再設定資料庫權限。


### 3.5：正規化 Normalisation

正規化是在檢查：**每種資訊是不是放在適合的地方，避免同一件事反覆保存而互相矛盾。**

假如每筆商品都重寫製造商電話，廠商改電話時可能要修改很多筆；漏改就會出現不同版本。把廠商電話集中放在製造商表，可以減少這類問題。

課程提到 1NF、2NF、3NF 與 BCNF。初讀先抓方向：一個欄位不要塞一串同類清單；資料應依賴它所描述的那個對象；不屬於同一個主題的資訊，考慮分表保存。正式判斷會用到「鍵」與「函數相依」，需要做設計時再深入。

> **商業例子｜供應商換電話，只改一個地方**
>
> 如果同一供應商的電話被重複寫在 50 筆商品裡，換電話就可能漏改。把電話放在供應商表，商品只保留供應商編號，就能集中維護同一項資訊。


**這個單元學到的能力：解釋資料為什麼可靠，以及如何從規則、操作與結構三方面減少錯誤。**

## 單元四：把觀念放進完整案例

### 4.1 網球案例、4.2 公車案例

最後一單元利用完整案例，串起前面的設計、建表與查詢。

閱讀網球案例時，觀察選手、賽事及比賽資料如何表達關係；閱讀公車案例時，觀察路線、站點及相關資料如何組織。重點是理解「為什麼這樣分表」「用什麼欄位連接」「這樣能回答哪些問題」。

你可以用同一組問題看每個案例：**要記錄什麼？誰跟誰有關？用什麼識別？哪些錯誤應被擋下？最後要查出什麼？**

> **商業例子｜設計一個維修店資料庫**
>
> 維修店要記錄客戶、維修單、零件及用料明細。先確認彼此關係，再建表與設定規則，最後查出「每位客戶有哪些維修單」與「哪些零件用量最多」。這是把前面各單元串起來的做法。


**這個單元學到的能力：說明一個完整資料庫從需求到結果的邏輯。**

## 和老師對談時，先能說清楚這五件事

下面是理解方向，不需要照背，也不表示課程已確認有口試。

| 老師可能問 | 你可以用自己的話表達 |
|---|---|
| 為什麼要分成幾張表？ | 不同事物分開管理，減少重複；需要完整資訊時，再透過識別欄位連起來。 |
| 主鍵和外鍵差在哪裡？ | 主鍵辨認本表的紀錄；外鍵用來連到其他表的紀錄。 |
| JOIN 在做什麼？ | 把有關聯的紀錄配對，例如讓商品資料顯示對應的製造商名稱。 |
| 為什麼要正規化？ | 避免同一資訊重複保存，造成新增、修改或刪除時出現不一致。 |
| SQL 沒報錯，答案就對嗎？ | 還要看條件與關係是否正確。例如 JOIN 少了配對條件，可能查出不該有的組合。 |

讀完後，回頭試著解釋：「我會怎麼保存一份選課資料？」能說出學生表、課程表、選課表，以及它們怎麼連接，就已經掌握這門課很重要的一部分。
